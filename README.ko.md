# Grounded — Finance & Healthcare RAG Demo

[English](README.md) | **한국어**

Grounded는 하나의 공통 RAG 아키텍처를 금융 상품 탐색과 의료 행정 안내라는 서로 다른 업무 도메인에 적용한 풀스택 포트폴리오 프로젝트입니다.

PostgreSQL과 pgvector에 저장된 도메인 문서와 세션 메모리에서 현재 요청에 필요한 근거를 검색하고, 도메인 및 역할 정책을 적용한 뒤 생성된 응답과 함께 인용 출처, 가정, 누락 정보 및 제외된 근거 그룹을 제공합니다.

**[라이브 데모 실행하기](https://rag-advisor-demo.onrender.com)**

> Render 무료 인스턴스가 유휴 상태에서 깨어나는 경우 첫 요청에 최대 약 1분이 걸릴 수 있습니다. 일반 브라우저 프로필에는 게스트 세션이 유지됩니다. 첫 방문 흐름을 다시 테스트하려면 시크릿(InPrivate/Incognito) 창을 사용해 주세요.

## 이 데모에서 확인할 수 있는 것

- 하나의 페르소나형 RAG 아키텍처를 여러 업무 도메인에 재사용하는 구조
- 활성 페르소나, 사용자 프로필, 세션 메모리, 도메인 문서, 검색 정책 및 LLM 오케스트레이션의 분리
- 현재 요청에서 명시한 가정과 정정 사항이 저장된 프로필 및 검색된 과거 메모리보다 우선하는 컨텍스트 우선순위
- 금융과 의료 행정 데이터의 도메인 분리 및 사용자 역할에 따른 근거 필터링
- 인용 출처, 가정, 누락 정보 및 제외 근거를 통한 응답 단위 추적 가능성
- 인증, 사용량 제한, 동시 요청 제한 및 서버 측 권한 검증을 포함한 공개 데모 운영 구조

## 주요 기능

- **금융:** 가상의 예금·적금 및 펀드 탐색, 사용자 투자 성향 메모리, 적합성 정책 기반 필터링, 근거 기반 상품 비교 및 추천 리포트 생성
- **의료 행정:** 가상의 병원 정책을 바탕으로 입·퇴원, 예약 변경, 의무기록 사본 발급 및 개인정보 처리, 원무 문의, HIS 계정과 접근 권한 절차 안내
- 한국어·영어 UI 및 질의 지원
- 런타임 스키마 검증을 거친 구조화 LLM 출력과 스트리밍 응답

## 프로젝트의 출발점과 아키텍처 재사용

이 데모는 장기 대화 맥락을 유지하기 위해 개발한 페르소나형 RAG 프레임워크 **Rita-Berenice**에서 확장되었습니다.

기존 프레임워크는 활성 페르소나, 사용자 및 세션 메모리, 도메인 지식, 검색 정책과 LLM 오케스트레이션을 서로 분리하도록 설계했습니다. 금융과 의료 행정 워크플로는 검색 및 기억 아키텍처를 새로 설계하지 않고 이러한 핵심 계층을 재사용합니다.

도메인을 전환하면서 주로 교체하거나 확장한 부분은 다음과 같습니다.

- 도메인 문서 및 fixture
- 페르소나와 사용자 프로필 스키마
- 적합성, 역할, 접근 권한 및 출처 정책
- 도메인별 검색 필터
- 구조화 응답 스키마
- 금융 및 의료 행정 워크플로 컴포넌트

이를 통해 기존 캐릭터 대화 용도를 넘어, 하나의 아키텍처가 서로 다른 업무 도메인의 페르소나형 AI 서비스에도 적용될 수 있음을 검증했습니다.

기존 프레임워크의 개념을 재사용하기 때문에 일부 화면과 내부 명칭에는 `Character`, `Lore` 등의 용어가 남아 있습니다.

- `Character`는 도메인별 상담자 페르소나를 의미합니다.
- `Lore`는 정제된 도메인 지식, 참고 자료 및 운영 정책을 의미합니다.
- 세션 메모리는 현재 워크플로에서 축적된 사용자별 맥락을 의미합니다.

이 개념들은 가상의 캐릭터 대화에만 한정되지 않고, 도메인별 AI 서비스를 구성하기 위한 재사용 가능한 추상화로 사용합니다.

## 안전 및 적용 범위

모든 금융 상품, 고객 프로필, 병원, 환자 상황 및 운영 절차는 데모를 위해 만든 가상 데이터입니다.

금융 도메인의 규제·교육 자료에 한해서만 출처와 기준일을 기록한 한국 공공 자료를 사용합니다.

이 애플리케이션은 엔지니어링 구조를 보여주기 위한 데모입니다. 실제 금융·법률·의료 자문을 제공하지 않으며, 실제 상품 추천, 전문가 안내 또는 진료 판단을 대신하지 않습니다.

공개 배포 환경에서는 회원가입과 문서 승인 등 관리용 데이터 쓰기 작업을 서버 계층에서 차단합니다. API 키와 데이터베이스 자격 증명은 서버 환경 변수로만 관리하며 클라이언트 번들 또는 저장소에 포함하지 않습니다.

## 아키텍처와 처리 흐름

1. 현재 요청, 도메인, 사용자 역할 및 세션 맥락을 정규화합니다.
2. 현재 요청에 명시된 가정과 정정 사항을 해석하고, 저장된 프로필과 검색된 과거 메모리보다 우선 적용합니다.
3. pgvector에서 관련 도메인 문서와 세션 메모리를 검색합니다.
4. 역할, 적합성, 도메인 분리 및 출처 정책에 따라 사용할 근거를 필터링합니다.
5. 선택된 근거를 포함한 프롬프트로 런타임 스키마 검증이 가능한 구조화 응답을 생성합니다.
6. 응답을 스트리밍하고 인용 출처, 가정, 누락 정보 및 제외된 근거 그룹과 함께 표시합니다.
7. 금융 워크플로에서는 별도로 검토할 수 있는 상품 추천 리포트를 생성합니다.

## 로컬 실행

### 요구 사항

- Node.js 22 이상
- pnpm 10.18.0
- 로컬 PostgreSQL, pgvector 및 SuperTokens 실행을 위한 Docker

```bash
pnpm install
pnpm db:up
pnpm dev
```

`.env.example`을 복사해 Git에서 추적하지 않는 로컬 `.env` 파일을 만들고 필요한 값을 입력합니다.

API 키와 데이터베이스 자격 증명은 커밋하지 마세요.

## 검증

고정 fixture 검증과 외부 모델 provider를 호출하지 않는 평가를 먼저 실행할 수 있습니다.

```bash
pnpm preflight:finance
pnpm eval:finance
pnpm preflight:healthcare
pnpm eval:healthcare
pnpm typecheck
pnpm test
pnpm build
pnpm format:check
```

데이터베이스 시드 및 실제 LLM·임베딩 스모크 테스트 명령은 기본적으로 dry run으로 실행됩니다.

예정된 데이터베이스 쓰기 작업과 외부 provider 호출을 검토한 뒤에만 명시적으로 `--apply`를 사용합니다.

## 배포

라이브 데모는 다음 환경을 사용합니다.

- 저장소의 Dockerfile로 빌드한 Render Web Service
- PostgreSQL 및 pgvector를 위한 Neon
- 인증을 위한 호스팅 SuperTokens

환경 변수와 배포 후 점검 절차는 [`docs/render-deployment.md`](docs/render-deployment.md)를 참고하세요.
